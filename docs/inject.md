# 主动注入:透明中转与 c2s 包构造

本文记录仓库里**唯一会主动发包**的那条链路:`internal/relay` 把游戏连接接管下来原样转发、
顺便插进自己的请求,`internal/petbox` 把「宠物盒换位」拼成与客户端同构的字节,
`cmd/boxarrange` 把两者串起来(用法见 `go run ./cmd/boxarrange -h`)。

> **与抓包链路的边界。** `internal/capture` 那一线仍旧是「不读内存、不注入进程、只解析网络
> 流量」,本文这条链路不在它上面,也不被它引用 —— 只有显式加 `-send` 才会打开 socket。
> 两者甚至不能同时工作:接管期间流量变成「手机↔网关」「网关↔服务器」两段,两段的一端都是
> 网关自己的 IP,而实时抓包会跳过本机 IP(单臂网关去重)。

分帧、密钥、internal header 这些**收发共用**的格式见 [protocol.md](protocol.md)。本文只补它
没覆盖的部分:**自己造包才会碰到的字段**,并对每条结论标明证据强度。

本文的统计取自仓库里全部 40 份抓包共 **19105 条 c2s DATA**(`-selftest -pcap pcap/*.pcap00 pcap/inject.pcap`
一次跑完;头块规则逐条核过,只有 2 条不过 —— 都是早期自己填错的注入),下行的结构细节另取自
其中 4 份直连抓包的 1755 条 s2c。`-selftest` 可以在任意一份新抓包上重跑(见第 5 节)。

另有一份 **22 分钟的完整会话**(`rocom-20260822-1543/1553/1603`,轮转成三份,经中转但不注入):
c2s DATA **10374 条**、上行序号涨到 10829(双向合计 24107),跨度 22m41s ——
上行全部 GCP 包折合 **7.95 包/秒**(只数 DATA 是 7.62),头块规则核过 10374 条**零例外**。

还有一条 **2026-08-22 在网关上边玩边核的长连接**(`-selftest -iface`,不落盘不发包;
客户端是 **Windows 版**,文档里此前只有安卓与 iOS):
同一条 TCP 连接**上行序号跨过了 65536**(观察到 70594 仍在涨,双向合计 12.8 万),
前后几个嗅探进程接力共核过 **6.5 万余条 c2s DATA 零例外**,其中序号 ≥65536 的那部分单独计数、
同样全过 —— 这是 `[1]` 唯一一次被真包用到,见 3.2 与第 5 节。

> **包速率随活跃度差好几倍**,别拿单一数字外推:实测上行 **3.2~8.0 包/秒**(挂机与打本差
> 一倍多),下行 13~30 包/秒。下面凡是按 7.95 包/秒折算的时长都是**最快的那一档**,实际更慢 ——
> 8-22 那条连接跨过 65536 用了约两小时,与「2 小时 17 分」这个估计恰好同量级。

> **样本偏差要先说清楚。** 上面那 40 份大多是几分钟的分析样本,22 分钟那条也只到序号 10829。
> 跨过 65536 的只有 8-22 那条长连接一份,`[0]`(序号 ≥ 2^24)则**从没被用过** —— 按 7.95 包/秒
> 要连续玩 24 天,现实中到不了。凡是「取值范围」类的结论(见 3.2)都只在观察到的区间内成立,
> 超出就是外推。程序对此有运行时兜底:每条客户端包都替我们核一遍,对不上就停用注入(见 2.4)。

## 1. 为什么必须做成中转

GCP 头里的 `sequence` 是**每个方向一个的逐包计数器**:从 1 起、每包 +1,SYN/AUTH/心跳/DATA
共用同一个计数(实测两个方向都如此)。所以**没法往一条现成的连接里凭空塞包** —— 插进去的那个
包会把客户端后续所有包的编号顶掉,服务端立刻看出流断了。

做成中转之后,客户端的包经我们的手转出去,给它们的编号加上「已注入的包数」即可无缝顺延。
代价是必须在网关上终结 TCP,好处是**只需要改几个字节**,其余(连 HEAD.extend)原样带过去。

## 2. 透明中转

### 2.1 接管方式

nftables 把手机发往 8195 的包 DNAT 到本地监听口,程序再向 conntrack 要回原始目的地:

```
sudo nft add table ip rocom
sudo nft add chain ip rocom pre '{ type nat hook prerouting priority dstnat; }'
sudo nft add rule ip rocom pre ip saddr 10.42.0.0/24 tcp dport 8195 redirect to :4940
# 用完删掉: sudo nft delete table ip rocom
```

- `saddr` 写**热点整个网段**而不是某台手机的 IP:换台设备 IP 就变了,规则匹配不上时游戏是
  直连的 —— 日志一片正常,其实什么都没接管到。以日志里「接管连接」那行确认真的接上了。
- redirect 之后 `conn.LocalAddr()` 已经是本机地址,真正的目的地要用 `SO_ORIGINAL_DST`
  (`SOL_IP`,选项号 80)取。取出来是 `struct sockaddr_in`,布局与 `syscall.IPv6Mreq` 一致,
  Go 里借它当容器(`internal/relay/origdst_linux.go`)。
- 规则加好后要把游戏切后台再切回来(或重登)让它重连一次,才接得到。

### 2.2 中转改哪些字节

| 方向 | 改动 | 说明 |
| --- | --- | --- |
| 上行 GCP 头 `[9:13]` | `+= 已注入包数` | 给注入的包腾出编号 |
| 上行 DATA 密文头块 `[0:4]` | 同步改成新序号 | **同一个序号在密文里还有一份完整 u32 副本**,见 3.2 |
| 下行 | **一个字节都不改** | 自己请求的回包也照转给客户端,只是顺带认领一份 |

除此之外上下行都是逐字节的管道(`TestRelayIsByteExactWithoutInjection` 钉着这一条)。

### 2.3 三条不变量

都是踩出来的,各有一个测试守着:

1. **顺延上行序号要改两处。** 只改 GCP 头那一份的话,注入之后客户端的每一条 DATA 都带着两个
   自相矛盾的序号。实测服务端接受并执行注入的换位(回 0x1888、游戏里确实生效),然后在收到
   注入之后**第一条客户端 DATA** 约一个 RTT 之后 SSTOP —— 三次实测断点全在这里,0.5~2.7 秒
   的差别只是客户端下次开口的间隔。两份一起改之后线上实测不再掉线。
2. **绝不改客户端的应用层请求序号。** 见 3.4。
3. **一次 Read 里的包必须一次写出去。** 逐包各写一次加上 `TCP_NODELAY`,手机原本塞在一个
   TCP 段里的十条消息到上游就成了十个小段。同路径下零解析、只做 `io.Copy` 的哑代理不掉线,
   而逐包写出的那一版每次都在客户端那条环境上报之后被踢。

### 2.4 运行时兜底:让客户端替我们验规则

头块规则是从抓包归纳的,而抓包覆盖不到长会话。好在**客户端自己的每一条包都带着答案**:
中转在改写序号之前,先拿它的头块解出序号与外层比一次(`petbox.HeaderSeq`,只要一个 AES 分组,
不用解整包)。

- 一直对得上 → 这条会话上规则成立,包括抓包从没覆盖过的序号区间。
- 有一条对不上 → 这个版本的头块不是我们理解的样子,**立即停用注入**并打日志。

`boxarrange -send` 每 15 秒报一次核过多少条,开跑前也会拦一道。猜错的代价是服务端把整条
会话判死,所以这里选择「不确定就不发」。`TestRefusesInjectWhenHeaderRuleBroken` 钉着这条。

## 3. 已确认的规则

### 3.1 c2s DATA 的 body

```
body = AES-128-CBC(key, IV=全零) 加密的 [16 字节头块 || 应用层明文]
body_len = 明文长度 + 16      明文长度恒为 16 的倍数
```

**那 16 字节不是随机 IV。** 把它当 IV、拿它去解后面的密文,数学上与「零 IV 解整段、丢掉第一块」
完全等价 —— 所以被动解析怎么读都对,`internal/gcp` 的 `embedded_iv` 分支一直工作正常。
但要自己造包就必须把它填对:早期填随机 16 字节,服务端解出垃圾,**收到即断开且不给 ret_code**,
一切「内容层面」的排查全落空,因为服务端压根没看到一个合法的包。

### 3.2 头块的构造

底子是一段 `buf[i] = i` 的递增填充,把一个结构体**异或**进去。异或掉填充之后,上下行各自是:

```
c2s  [0:4]  u32  GCP 包序号(见下,只有最高字节还是外推)      19103/19105
     [4:6]  u16  恒为 0x55aa(与 s2c 应用层明文那个标记同值)  19103/19105
     [6:10] u32  protobuf body 长度 + 26                    19103/19105
     [10:16]     逐包在变的残留,见下

s2c  [0:2]  u16  恒 0                                       1755/1755
     [2:6]  u32  protobuf body 长度 + 26(与 c2s 同一条规则)  1392/1392
     [6:10] u32  跨会话复现(见 4:同一服务器上七周里都是 0x320cb979)
     [10:16]     恒 0                                       1755/1755
```

三条要点:

- **序号至少是 24 位已实测,按 32 位填,只有最高字节是外推。** 只异或低字节的话前 255 个包
  看着都对,之后每一次注入都会被服务端判死。`[3][2]` 早有大量样本;`[1]` 由 8-22 那条长连接
  验到 —— 同一条连接的上行序号从 5.4 万一路涨过 65536(最高见到 67540),跨过边界的那批包
  头块规则**一条不差**,证明 `[1]` 确实是同一个 u32 的第三字节,而不是「另一个恰好恒 0 的字段」。
  `[0]` 仍是外推(要序号 ≥ 2^24,连续玩 24 天),靠 2.4 的运行时兜底。旁证也仍然成立:同结构的
  长度字段 `[6:10]` 第三字节本就会被用到(大包 `[8]` 取到 0~3)。`TestBuildHeaderWideSeq` 钉着填法。
- **长度字段上下行同规则**,都是 `protobuf body 长度 + 26`,只是落在不同偏移
  (c2s 的 internal header 是 14 字节、s2c 是 10 字节,所以按明文长度写会差 4)。
  填错与序号填错同样致命:服务端解出垃圾,收到即断且不给 `ret_code`。
- **`[10:16]` 逐包在变、分布逐客户端不同,照抄当前连接最常见的那份。** 一份 iOS 抓包里同一个 opcode 能出现二十几种
  取值、同一秒内乱跳(所以服务端显然不看);22 分钟那台 10374 条包里也有 7 种取值,只是
  `000000000001` 一家占了 99.0%,余下那 1% 连 `[14:16]` 都在变。像是「有的实现清了结构体尾巴、有的没清」。
  既然连恒定都算不上就别猜:`relay` 从当前连接学一份最常见的照抄,与 `head6`/`tag` 同理
  (`TestInjectCopiesClientHeaderTail` 钉着)。

`petbox.BuildHeader` 按这套规则**从零构造**,不需要从真包里学任何东西;
`petbox.RenumberSeq` 只改 `[0:4]` 那份序号再重新加密,用于中转顺延客户端包的序号;
`petbox.CheckHeader` 反过来校验前 10 字节,`boxarrange -selftest` 拿它在真包上逐条复核。

**下行没有序号副本。** 1755 条 s2c DATA 里没有任何一个字节是包序号的镜像(各字节「碰巧相等」
的比率都在 1/256 的随机水平),所以中转转发下行时一个字节都不用动。

### 3.3 应用层明文与尾部

```
00000000  45 b4 c7 20 00 01 18 87  28 00 00 00 00 38 0a 09  |E.. ....(....8..|
          └ head6  ┘└op ┘└tag┘└ reqSeq ┘└ protobuf ...
                                      ... ┘└ 填充 ┘└"tsf4g"┘└尾长
```

- 明文总长恒为 16 的倍数(323/323 条统计)。AES-CBC 没有 PKCS7,靠尾部那段填充对齐,
  最后一字节写明尾部总长(填充 + `"tsf4g"` + 自己),接收方据此剥掉。
- **填充是随机字节,不是校验和。** 光看「按长度分组两两不重复」证明不了(校验和也不重复),
  真正的证据是:我们发的填充取自 `crypto/rand`,服务端照收不误。整条 c2s 消息里没有任何
  完整性校验,这也是伪造一条成本极低的原因。
- `head6`(`[0:6]`)与 `tag`(`[8:10]`)**不是常量**。取值像 16 字节对齐的指针
  (`45b4c720` / `02a7c350` / `6d07a7b0` …),一条会话里 `[8:10]` 能出现三十几种值,
  跨会话跨版本全不一样 —— 是客户端结构体里没初始化的填充。真发时由中转从当前连接观察到的
  请求里学一个最常见的照抄(`relay.Conn.template`),离线模拟才退回 `petbox.DefaultTemplate`。

### 3.4 两套序号

| | 位置 | 规则 |
| --- | --- | --- |
| **GCP 包序号** | 外层头 `[9:13]`,明文;c2s 另有一份完整 u32 在密文头块 `[0:4]` | 每方向一个,从 1 起逐包 +1,所有 command 共用 |
| **应用层请求序号** | c2s 明文 `[10:14]`,密文里 | 请求↔回包的配对标记,服务端原样抄回 s2c `[6:10]` |

**请求序号不按发送顺序递增。** 客户端会给要成批发的请求**预分配号段**,而单独插进来的请求
抢到大号却先发了出去:

```
上线请求号 1 2 3 4 5 6 20 7 8 9 … 19 21 22 …
                     └ 环境上报,走另一条代码路径
```

曾按到达顺序给客户端的请求重新编号,想让服务端看到一条连续的号列,结果每次都在这条上报之后
约 25ms 被 SSTOP。既然客户端自己的号都不连续,服务端显然不在乎连续性,那就没有任何理由动它。
自己的请求从「客户端当前最大号 + 100000」取号:隔得够远才不会撞上它预分配出去、马上要用的号
(撞上就会误认领它的回包),而一次会话客户端也就发几百到上千个请求,追不上来。

### 3.5 盒位交换 `ZONE_PET_BOX_CHANGE_PET_REQ` (0x1887)

```
ZonePetBoxChangePetReq{ ori_info=1, tar_info=2 }
PetBoxPetChange{ pet_gid=1, is_in_team=2, id=3(盒号), pos=4(格号) }
```

- 盒子是 **6 列 × 5 行**,`pos = (行-1)×6 + 列`,1 起;`pet_box.slot` 是 0 起,故 `pos = slot+1`
  (2026-08-22 抓包里三次手工操作逐个对上)。
- `tar_info.pet_gid = 0` 表示目标格是空的,**成立**,而且可以跨盒(抓到客户端把盒5 格19 的
  宠物送进盒4 格6 的空位)。跨页拖动时游戏 UI 不让选具体格子,但客户端自己算了一个空格填进
  `pos` —— 所以我们反而能指定得比 UI 更精确。
- 回包 `0x1888` 带 `ret_info.ret_code` 与各宠物的落位,`cmd/boxarrange` 逐条核对后才走下一步。
- 字段顺序**每条会话重新定**,而且**外层也会反**。把仓库里带 `0x1887` 的抓包逐份跑一遍:

  | 抓包(客户端地址) | 外层(ori/tar) | 内层 PetBoxPetChange |
  | --- | --- | --- |
  | 8-15 164014(10.0.3.201) | 1,2 | `2,3,1,4` |
  | 8-22 003405(10.0.3.201,三条) | 1,2 | `4,3,2,1` |
  | 8-22 013007(10.42.0.215) | **2,1**(`tar_info` 先发) | `2,1,3,4` |
  | 8-22 014514(10.42.0.37) | 1,2 | `1,4,3,2` |
  | 8-22 015616(10.42.0.37) | **2,1** | `2,4,1,3` |
  | 8-22 154331(10.42.0.215,两条) | 1,2 | `2,1,4,3` |
  | 本工具 `EncodeSwap` | 1,2 | `4,3,2,1` |

  六份真包出了**六种顺序**,比在场的设备还多,所以此前「安卓/iOS/Windows 各一种」的读法
  不成立。真正的规律是:**同一条会话里恒定**(003405 那三条、154331 那两条各自一模一样),
  **换一条会话就变** —— 最直接的一组是 `10.42.0.37`,相隔 11 分钟的两条会话,内层从
  `1,4,3,2` 变成 `2,4,1,3`、外层还从 1,2 翻成 2,1。像是序列化时遍历了一张**按进程随机化**
  的哈希表。两条推论:「与真包逐字节一致」一般做不到,只能比语义(`-selftest` 就是这么判的);
  而六种顺序全被服务端照单全收,说明它确实不看顺序(protobuf 本来也不要求有序)。
  `-selftest` 仍会把顺序打出来(`内层字段顺序 2{2,1,3,4},1{2,1,3,4}`),但那是**这一条会话**
  的观察值,别拿它认设备。
- 三条 Windows 真包的 `tag`(明文 `[8:10]`)都是 `b388`,而 `head6` 三条各不相同 —— 同一台
  iOS 上 `tag` 能出三十几种值,这里却没变。样本只有三条、还全是 `0x1887`,分不出是「这台
  客户端的 tag 稳」还是「tag 与 opcode 有关」,好在 relay 本来就是从当前连接学、不写死。

## 4. 还属于猜测的部分

按 3.2 那轮统计,原先列为猜测的几条已经定下来了:`[2]` 是 u32 序号的第三字节(不是独立标志位)、
`[6:8]` 是 u32 长度的高半(不是独立字段)、s2c `[4:6]` 是长度字段的低半、s2c `[10:16]` 恒 0。
剩下这些仍然只是观察:

| 项 | 现状 | 影响 |
| --- | --- | --- |
| c2s 头块 `[10:16]` | 逐包在变,分布逐客户端不同:iOS 那台同一秒内能出二十几种值;**Windows** 那条长连接的两段样本分别是 12 种/98.6%、9 种/92.8%(众数都是 `000000000001`),少数派连 `[14:16]` 都在变。「未初始化残留」还是「某个没认出来的小字段」仍分不出,但**没有任何一台是恒定的** | 照抄当前连接客户端自己的那份,不猜 —— 98.6% 的众数让 relay「学最常见那份」很稳。真是残留的话它还会**泄漏客户端栈上的字节**,只是我们用不上 |
| `[6:10]` 里的偏置 26 | 上下行同值,c2s 19103 条、s2c 1392 条都成立,但对不上任何一段的自然长度(internal header 14/10、tsf4g 尾 6 都不是) | 大概是 tsf4g 框架自己那层的固定开销。没有解释就意味着换版本可能变,靠 `-selftest` 兜 |
| s2c 头块 `[6:10]` | **不是每会话随机**:7-04、7-18(两份)、8-22 那条实时长连接,四次独立的手机直连、跨七周,值全是 `0x320cb979`。另一个值 `0x340c81aa` 来自 8-22 经中转的那条 22 分钟会话 —— 那份抓包还在(`rocom-20260822-1543/1553/1603`),复核过**服务器 IP 同样是 `122.192.37.43`**,可见它不是按服务器 IP 分的。两个值还都是 `??0c????` 的形状 | 我们不构造下行包,不影响。同一个 IP 出两个值,「后端实例/连接句柄」比「路由标识」更像;到底是分到了别的实例,还是「中转换了源地址」所致,两份样本仍分不出 |
| **服务端到底校验了什么** | 只能从行为反推:`[0:4]`(序号)和 `[6:10]`(长度)填错必被断开;`[10:16]` 填任意值都没事;`[4:6]` 没试过填错 | tsf4g 的 TConnd 有 `CheckSequence` 配置项,与观察吻合,但没有源码佐证 |
| 序号字段的最高字节 `[0]` | `[1]` 已由 8-22 那条长连接验到(上行序号涨过 65536,规则不变),`[0]` 要序号 ≥ 2^24 才用得到 —— 按 7.95 包/秒得连续玩 **24 天**,真包里恒为 0 | 只影响超长会话。由 2.4 的运行时兜底守着:客户端自己的包一旦对不上就停用注入 |
| 请求号 100000 的提前量有没有上限 | 试过十万级、248、复用旧号,都能被接受,上限仍未知。反过来「够不够用」已经量出来了:客户端涨号速度实测 **903~6026 号/小时**(随活跃度差 6 倍),`+100000` 对应 **17~111 小时**连续游戏 | 撞不上客户端的号就行(等回包只有几十毫秒,客户端不可能在这期间涨十万个号)。再长的单局也追不上来 |
| 注入会不会留下服务端可见的痕迹 | 未知 | 包本身与客户端同构,但发包节奏是我们控制的 |

另外两条**已被推翻**的猜测,留在这里免得再走一遍:

- ~~「注入必然赔上这条连接,服务端收到的请求数与客户端计数对不上」~~ —— 根因是序号副本没同步,
  改对之后连接不掉。
- ~~「中转顶替了一跳路由却没减 TTL,或 TCP 指纹对不上」~~ —— 补 TTL、挂 netem 补握手延迟都试过,
  与掉线无关;上游本来就是 clash 透明代理,网关内所有流量都是这个形状。

## 5. 换版本时怎么复核

```
go run ./cmd/boxarrange -selftest -pcap pcap/<抓包>
go run ./cmd/boxarrange -selftest -pcap pcap/rocom-20260822-1[56]*.pcap00   # 轮转的多份连读
go run ./cmd/boxarrange -selftest -pcap pcap/*.pcap00 pcap/inject.pcap      # 全部语料一次跑完
```

拿抓包里真实的 `0x1887` 回来重建、与原字节比对,并把中转依赖的协议假设逐条复核:

```
== 协议假设自检(c2s DATA 10374 条,3 份抓包连读)
  ✓ 明文长度全部 16 字节对齐(10374/10374)
  ✓ 尾部都是 [填充]["tsf4g"][尾长]
  ✓ 头块 [0:4]=包序号、[4:6]=0x55aa、[6:10]=body 长度+26 全部成立(10374 条)
    ~ 单条连接上行包序号只到 10829(共 1 条连接,最长的是第 1 条;双向合计到过 24107),[0:2] 从没被用到 —— 这份样本验不了 65536 以上
  ✓ 请求序号 1..750 共 750 条无重号(其中 1 处不按发送顺序递增)
  ✓ 请求与回包严格 1:1(750 对,另有 22901 条回声为 0 的通知)
  · 请求外壳(明文 [0:6]/[8:10])共 73 种取值 —— 逐包不同,确认该学不该写死
```

头块那一条是最要紧的:它是唯一「被动解析永远看不出问题、自己造包却必须填对」的规则,
填错的后果是整条会话被静默判死。为此 `capture.Message` 带上了 `Sequence` 与 `Header` 两个
字段(被动链路本身不用)。手工拖一只宠物换位再抓,组包那一半才验得到;协议假设那一半任意
抓包都能验。

### 想验序号高位字节:玩一局长的

`[1]`(序号 ≥ 65536)按实测的 7.95 包/秒要玩满 **2 小时 17 分**才会被用到 —— 2026-08-22
用下面「被动嗅探」那条路验过一次(实测约 2 小时,上行涨过 65536,规则不变);`[0]` 要 24 天,
现实中到不了。换版本想重验,或者要落盘留证,抓长包时有四个坑:

- **`-W` 配 `-G` 是「到数就退出」,不是环形。** 脚本默认 `-G 600 -W 50` → 8 小时 20 分自动停。
  要更久就加 `-W 100`。文件按时间戳命名,不会互相覆盖。
- **必须从游戏建立连接之前开始抓。** 会话密钥只在 `0x1002 ACK` 里明文下发一次,漏了这一份
  后面全是密文。也因此**单独喂中间任何一份都会得到「一条 c2s DATA 都没解出来」** ——
  必须几份一起给 `-selftest`(`capture.RunOfflineFiles` 把它们当成一条连续的流)。
- **序号是每条 TCP 连接各自从 1 开始的。** 游戏中途重连(切后台、断网、换网)就归零,
  抓够时长不等于序号够大。自检末尾那行会直接报观察到的序号上限,别自己猜。
- **只有上行那个数算数,下行涨得快得多。** 头块只在 c2s 有,`[1]` 验没验到得看上行序号;
  而下行包量是上行的好几倍(实测 1439 条 c2s 的那份抓包里,上行序号才 1590,双向合计已到
  13580),拿双向的数当上行看会**早两三倍误判成验过了**。自检两个数都报,认「上行」那个。

体积不是问题:实测约 **29 MB/小时**,跑满 8 小时也就 240 MB 左右。

### 更省事的办法:被动嗅探,边玩边核

```
sudo go run ./cmd/boxarrange -selftest -iface wlo1
```

一个字节都不发、什么规则都不改 —— 与 `rocom-capture` 同样是纯 AF_PACKET 被动抓包,只是把
消息喂给协议假设自检而不是入库。不落盘、不用事后分析,Ctrl-C 打最终报告:

```
· c2s 226 条,头块规则 ✓(核过 226 条),最长连接上行序号到 54706(双向 94656,共 1 条连接)
· c2s 319 条,头块规则 ✓(核过 319 条,其中 319 条 ≥65536),最长连接上行序号到 67540(双向 113207,共 1 条连接)
```

两行都是网关上接上同一条已经跑了一个多小时的连接之后打的,`[1]` 就是这么验到的:

- **上行与双向差 1.73 倍**(54706 / 94656)。只报混合的那个数会在上行还没过 65536 时就
  报「用到了 `[1]`」—— 早两三倍的假阳性,所以两个数都报,认「上行」那个。
- **`其中 N 条 ≥65536` 是关键的那个计数。** 跨越边界的样本里总数说明不了高位区验过多少条;
  接上去之后每一条都在高位区,这个数与「核过」相等就说明整段都是高位样本。
- `c2s` 与「核过」都是**本进程**启动以来的,重启归零;序号不会,它跟着连接走 —— 所以借
  `-db` 的密钥重启一次,就能把统计口径切换成「只数高位区」,而不必让游戏重连(重连才真归零)。

Ctrl-C 之后除了协议假设,还会打一段**字段观察**:不判对错,只记那几个「还属于猜测」的字段
在这份样本里的分布,用来喂第 4 节那张表。

```
== 字段观察(不判对错,只记分布;换版本/换客户端时看这里)
  头块 [10:16] 残留:12 种取值,最常见 000000000001 占 98.6%
    [14:16] 也在变 —— 更像未初始化的栈字节
  s2c 头块 [6:10]:1 种取值 0x320cb979(6165 条) —— 「每会话恒定」在本样本上成立
  c2s protobuf body 最大 213 字节(长度字段 包太小,第三字节 [8] 没用到)
  跨度 5m39s:上行 4.76 包/秒、下行 18.20 包/秒
  请求号 5029..5114,约 903 号/小时 —— 注入取 +100000 的提前量够用 111 小时
```

**嗅探期间在游戏里手动拖一只宠物换位**,组包那一半也能就地验:实时模式与 pcap 模式一样,
会把抓到的真实 `0x1887` 拆开重建、与原字节比对,并把字段顺序打出来(每条会话都不一样,见 3.5,
只当这一条的观察值)。没拖过就只会提示「嗅探期间没见到 c2s 0x1887」。

两个进程可以同时跑(内核给每个 AF_PACKET socket 各一份拷贝),所以想换一份统计口径时
不必停掉正在跑的那个 —— 直接起第二个,各看各的。

**网关上已经有别的透明代理时(如 clash 挂在 iptables mangle)首选这个** —— 中转那条路要再插
一层 nftables 重定向,不划算,而这里与代理链路完全无关。

跑在网关上就 `make release` 交叉编译(afpacket 要 cgo,Makefile 里已经用 zig 备好 musl 静态
链接),把 `dist/boxarrange-linux-arm64` 拷过去和 `rocom-capture` 一起跑:

- 两个进程各开各的 AF_PACKET socket,内核给每个一份拷贝,不抢包也不互相影响。
- `-db` 指向 rocom-capture 的库,**只读**借它落盘的会话密钥 —— 这样已经建立的连接也能接上,
  中途重启自检不必让游戏重连(重连会让包序号归零,那正是要避免的)。借不到就只是回到
  「必须在建连之前开着」而已,不影响别的。
- 全部解密与统计都在内存里,不写库、不发包。

中转跑起来时也在做同一件事(2.4),`-send -relay-only` 每 15 秒报一次;两条路验的是同一条规则,
按手头方便挑一个即可。
